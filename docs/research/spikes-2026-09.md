## How the numbers were taken

- **End-of-frame recorder** (`src/lib/rec.js`). A 1px probe is resized from a rAF callback every frame, and its ResizeObserver callback samples the page. HTML runs every rAF callback, then style and layout, then resize observations, then paint. So the sample sees the frame as it will be painted, whichever order the libraries registered their rAF callbacks in. There is one row per rendered frame. Producers log with `document.timeline.currentTime`, which is equal to the rAF timestamp in both engines (checked).
- **Lag in frames.** `k` means the consumer shows the scroll offset the document had `k` frames earlier, so 0 is the same frame. It is counted only on frames where the scroll moved (> 0.5 px; ≥ 4 px for pixel readouts, where the noise is about 1.5 px).
- **Errors in scroll px.** An error is expressed as how far the scroll would have to move to explain the discrepancy, so a one-frame lag shows up as one frame's scroll delta.
- **Input.** `page.mouse.wheel(0, ±100)` notches 35–40 ms apart, plus `window.scrollTo` jumps, plus `lenis.scrollTo` where Lenis is present. Under Lenis the scroll moved a median 12 px per frame (p95 38–41, max 1,500 on jumps).
- **Painted readout** (S1, S3). S1 uses Playwright's `page.screencast` JPEG frames and S3 uses screenshots. S1's boxes self-check inside each image. Control boxes positioned by JS in the callback that moves the scroll show whether the capture can be trusted.

## S1 — Lenis + CSS scroll/view timelines (Chromium, WebKit)

**Question.** With Lenis smoothing the wheel (`autoRaf: false`, driven from our own rAF), do `animation-timeline: view()` and `scroll(root)` track the smoothed scroll with no extra lag or jitter?

**Setup.** `pages/s1.html`, 1000×600.
- Five `view()` boxes animate `transform: translateX(0 → 400px)`, which the compositor can run. Five more animate `left`, which runs on the main thread.
- One `position: fixed` box of each kind runs on `scroll(root)`. They do 8 iterations over the page so that one painted px is about one scroll px.
- Five control boxes are positioned by JS in the rAF callback right after `lenis.raf()`, so they are in sync by construction.
- The native baseline is the same page without Lenis.

**Method.** Each engine × mode gets three JS runs and two screencast runs, then a timing-only run and a style-only run. The single-read runs gave the same lag counts, so reading one quantity does not disturb the other. The JS readout compares each box's `getComputedTiming().progress` and computed `transform`/`left` with the progress that `scrollTop` implies in that frame. The painted readout checks each view box's x against its own painted top, and each fixed box against the scroll offset read from a visible view box. Every capture is joined to its per-frame row to count lag in frames.

Lag histograms over moving frames, all runs pooled:

| Readout | Chromium + Lenis | WebKit + Lenis | Chromium native | WebKit native |
|---|---|---|---|---|
| JS `view()`: transform · left | 0 frames: 1125/1130 · 1045/1050 | **1 frame: 978/998 · 928/948** | 0: all | 0: all |
| JS `scroll(root)`: progress · computed transform | 0: 1188/1188 · 1188/1188 | **1: 1015/1035** · 0: 1035/1035 | 0: all | 0: all |
| JS max / p95 error | 14 / 0 scroll px | 92 / 40 scroll px | 0 | 0 |
| Painted `view()` transform | 0: 262/262 | 0: 35 · **1: 39** | 0: 32/32 | 0: 28 · **1: 13** |
| Painted `view()` left | 0: 232/232 | **1: 68/68** | **1: 26/26** | **1: 44/44** |
| Painted `scroll(root)` transform | 0: 284/284 | 0: 39 · **1: 41** | 0: 36/36 | 0: 36 · **1: 18** |
| Painted `scroll(root)` left | 0: 284/284 | **1: 80/80** | **1: 36/36** | **1: 54/54** |
| Painted JS controls | 0: 232/232 · 284/284 | 0: 65/65 · 80/80 | **1: 28/28 · 36/36** | **1: 44/44 · 54/54** |
| Painted max / p95 error | 2.4 / 1.7 px (controls 1.6) | 85 / 38 px | ≈ 100 px (one notch) where late | ≈ 100 px (one notch) where late |

Under Lenis the scroll moved a median of 12 px per frame in Chromium (p95 38) and 10 px in WebKit (p95 41). Native wheel scrolling jumps 100 px per notch. The WebKit native painted column also includes an extra run of four screencast passes with 30 notches each way, because the first runs caught only 8 moving frames. That run is `ENGINES=webkit MODES=native REPS=0 CAST_REPS=4 SINGLE_READ=0 WHEEL_DOWN=30 WHEEL_UP=30 OUT_SUFFIX=-webkit-native-cast npm run s1`, and it writes `results/s1-webkit-native-cast.json`. Chromium's five one-frame JS samples are the frames in which a `view()` box re-enters its range from the after side while scrolling up, once per re-entry. At that moment the box is cut off at the top edge of the viewport, where the painted readout can't measure it.

**Verdict: partly.**
- **Chromium: yes.** CSS timelines are frame-exact under Lenis, in JS and in painted frames, for compositor and main-thread properties alike.
- **WebKit 26.6: no.** Timeline values come from the previous frame's scroll in 98% of moving frames. Painted `left` is one frame late in every frame. Painted `transform` alternates between 0 and 1 frames (80/154 late, 52%), which is jitter of up to one frame's scroll (p95 about 37 px at 60 Hz). The JS controls paint in sync under Lenis, so the capture is faithful. The practical cost is that under Lenis in Safari, CSS-timeline effects fall a frame out of step with anything driven from Lenis's tick.
- **WebKit native is not frame-exact either.** Painted `transform` is late in 31/95 frames (33%) and `left` in 100%. So Lenis makes a loose engine slightly looser (52% against 33% for `transform`); it doesn't break a working one.
- **Native side finding (Chromium).** Under native threaded scrolling, only compositor-run timeline animations (`transform`) track the painted scroll exactly. `left`, and JS written from `scrollTop`, paint one frame late (both engines). That is the known threaded-scroll gap, not a Lenis problem. It is also the one place where "transform/opacity only" is about correctness, not just cost.

**Rule.** Under Lenis, CSS `scroll()`/`view()` timelines are frame-exact in Chromium but read the previous frame's scroll in Safari 26. There, use them only where a one-frame offset is invisible (decoration, progress, fades), and drive anything registered to moving content from Lenis's tick.

**Caveats.**
- WebKit here is Playwright's build, not Safari. Its screencast samples about 22 fps; every captured frame is self-checked and the controls validate the capture. Confirm on the real-device pass.
- At 120 Hz the per-frame error halves (Lenis caps Safari at 60 fps anyway).
- In WebKit, JS readouts disagree with each other: the computed transform of the fixed box reads current while its timing progress and painted frames lag. Trust painted frames there.

## S2 — What breaks under ScrollSmoother (Chromium)

**Question.** Inside `#smooth-wrapper > #smooth-content` (`smooth: 1`), do these still work: sticky, a `view()` timeline, Motion `useScroll` (against a ScrollTrigger on the same element), IntersectionObserver and `whileInView`?

**Setup.** `pages/s2.html` (React), 1280×720. The baseline is the same page without ScrollSmoother. ScrollSmoother makes the wrapper `position: fixed; overflow: hidden`, so the wrapper is the scroll container its children see, and it never scrolls. Every probe is checked against the element's visual position (`getBoundingClientRect`, which includes the content transform).

**Method.** Two runs per mode: wheel 45 notches down, then 18 up, then a `scrollTo` jump. The smoothed content trailed the native scroll by a median of 43–48 px (p95 241, max 267).

| Probe | Native | ScrollSmoother |
|---|---|---|
| (a) sticky child, inside its travel zone | top = 0 in 120/120 frames: it sticks | top = its range's top in 130/130 frames: it scrolls away with the content (up to 1,588 px off) |
| (b) `view()` progress | matches the visual position (error 0) | stuck at 0 for the whole run while the visual progress goes 0 → 1 (error up to 0.985) |
| (c) Motion `useScroll({ target, offset: ['start end','end start'] })` vs ScrollTrigger on the same element | 0 px apart | **up to 244 px apart while moving** (p95 241, median 25–28), ≤ 2.2 px at rest. Motion equals the unsmoothed layout exactly (0 px); ScrollTrigger equals the visual position (0 px) |
| (d) IntersectionObserver / `whileInView` | fire in the frame of visual entry | fire in the frame of visual entry (rect top 715 of 720), 150 ms (9 frames) after the unsmoothed layout crossed |

**Verdict.**
- **(a) No.** Sticky doesn't stick.
- **(b) No.** `view()` doesn't progress.
- **(c) No while moving, yes at rest.** Motion follows the native scroll offset, which ScrollSmoother leaves unsmoothed, so Motion runs ahead of what you see by the smoother's lag.
- **(d) Yes.** IntersectionObserver and `whileInView` fire on the element's visual entry.

**Rule.** Inside ScrollSmoother's content, sticky and CSS scroll/view timelines don't run, and Motion `useScroll` reads the unsmoothed scroll. So ScrollSmoother routes take every scroll-linked value from ScrollTrigger (pins included) and use IntersectionObserver/`whileInView` only for entrances.

**Caveats.** Measured in Chromium only, as the brief asks; the mechanisms (a fixed wrapper, a transformed content element) are engine-independent. The Motion gap scales with `smooth` and scroll speed.

## S3 — Motion 13.4 accelerated scroll over a sticky pin (Chromium, WebKit)

**Question.** Does Motion promote `style={{ opacity }}` to a native ScrollTimeline or ViewTimeline animation? Here `opacity = useTransform(scrollYProgress, [0.2, 0.6], [0, 1])`, with `useScroll({ target: range, offset: ['start start','end end'] })` over a sticky `100lvh` pin. If it does, does the computed opacity agree with `mv.get()`, especially past the range end and while scrolling back? And is writing by hand still required?

**Setup.** `pages/s3.html`, 1280×720. Every variant renders two elements: a bound `motion.div style={{ opacity }}`, and a control written by hand (`useMotionValueEvent(opacity, 'change', v => el.style.opacity = v)`). The variants:
- `brief`: the brief's geometry (400vh range);
- `brief-padded`: input padded to `[0, .2, .6, 1] → [0, 0, 1, 1]`;
- `cover`: offset `['start end','end start']`;
- `v1`: v1's FadeOnExit geometry, with the copy under `marginTop: -100lvh` over the pin and offset `['start start','end start']`, `[.1, .35] → [1, 0]`;
- `v1-tall`: the same with the copy 130vh tall;
- `no-target`: `useScroll()`, no pin.

`m.div` under `LazyMotion strict` gave the same numbers as `motion.div`.

**Method.** A stepped scan down and back up (41 settled positions each way). At each position we record `mv.get()`, both elements' computed opacity, and their painted opacity from a screenshot (a black box over a known background). Then a continuous wheel pass with the per-frame recorder. Chromium and WebKit matched to three decimals.

| Variant | What `getAnimations()` shows on the bound element | Max \|computed − mv\| | Max painted error | Hand-written control |
|---|---|---|---|---|
| brief | `Animation` on `ViewTimeline`, range `contain 0%`–`contain 100%`, keyframes `0.2:0, 0.6:1`, fill both; inline opacity `"0"` | **1.00**: from 0.6 to 1 it fades back to 0.01 where mv is 1, then stays 0 past the end | 0.987 | 0 |
| brief-padded | same timeline, keyframes `0:0, 0.2:0, 0.6:1, 1:1` | 0 | 0.004 | 0 |
| cover | nothing (not promoted) | 0 | 0.005 | 0 |
| v1 | `ViewTimeline`, `exit 0%`–`exit 100%`, keyframes `0.1:1, 0.35:0`; inline `"1"` | **1.00**: past 0.35 it fades back **in** | (off screen by then) | 0 |
| v1-tall | same as v1 | **1.00**, and 0.785 inside [0.1, 0.35] | 0.783 in range, 0.584 fading back | 0 |
| no-target (no pin) | `Animation` on `ScrollTimeline` (root), keyframes `0.2:0, 0.6:1` | **1.00** | 1.00 | 0 |

**Why.** Motion passes the useTransform input range straight through as WAAPI keyframe offsets, `element.animate({ opacity: [0, 1], offset: [0.2, 0.6] }, { fill: 'both' })` (motion-dom's `startWaapiAnimation`), and adds no keyframes at 0 and 1. WAAPI fills the missing ends with the element's underlying value, which is Motion's first-render inline opacity. So outside `[from, to]` the native animation slides back toward that first value instead of holding. That reproduces v1's "faded back in over the next 600px". v1 blamed the pin's range disagreement, but the pin was never the cause: `no-target` fails with no pin at all.

There is a second, smaller trap. Motion maps these offsets to named ranges that only match its JS ranges for one subject size:

| Motion offset | Named range | Matches Motion's JS range only when the subject is |
|---|---|---|
| `['start start','end start']` | `exit` | shorter than the viewport |
| `['start end','end end']` | `entry` | shorter than the viewport |
| `['start start','end end']` | `contain` | taller than the viewport |

The v1-tall copy is taller than the viewport but uses `exit`, which is the 0.785 error inside the range.

**Verdict: yes, still required, and not only over pins.** The promoted path is wrong whenever the input range doesn't span 0–1 (and inside the range, on size-mismatched presets). The hand-written path matched `mv` exactly in both engines (error 0, painted ≤ 0.004).

**Rule.** Write scroll-linked styles by hand (`useMotionValueEvent`), or pad every input range to 0 and 1. Motion 13.4 hands a scroll-linked opacity, clipPath, filter, backgroundColor or transform to a native timeline when `useScroll` has no target or uses one of its four preset offsets. Those keyframes stop at the input range, so outside it the element drifts back to its first-render value.

**Caveats.** Only those five style keys are promoted; `x`, `y` and `scale` never are. Only no-target and the four preset offsets are promoted: `['start end','end end']` (entry), `['start start','end start']` (exit), `['start start','end end']` (contain) and `['end start','start end']` (cover). The usual `['start end','end start']` is not. Padding fixes the ends but not the size-class mismatch, so hand-writing is the safer default.

## S4 — Same tick (Chromium; WebKit for a and b)

**Question.** Is each consumer's value from the frame whose scroll it paints with? Three consumers:
- (a) a `scrub: true` ScrollTrigger tween fed by Lenis;
- (b) Motion `useScroll` (written by hand) and a `useSpring` of it;
- (c) an R3F plane placed from a DOM box's cached rect plus the current scroll.

**Setup.** `pages/s4a.html`, `s4b.html`, `s4c.html`, 1000×600. Each mode gets three runs of: wheel 14 notches down and 7 up, then `lenis.scrollTo(1500)`. At the end of every frame we sample `scrollTop` and each consumer's value, and count the lag *k* for which the value equals what `scrollTop` from *k* frames earlier implies (±1 scroll px). S1's controls showed that main-thread writes made under Lenis paint in the frame they are made, so for (a) and (b) this readout is the painted state. For (c) it is the logical lag the brief asks for: the scroll value the render used.

**(a) GSAP.** Lag of ScrollTrigger progress and of the tween's transform (identical columns):

| Lenis driver | Chromium | WebKit | Max error |
|---|---|---|---|
| `gsap.ticker.add(t => lenis.raf(t * 1000))`, `lagSmoothing(0)`, `lenis.on('scroll', ScrollTrigger.update)` | 0 frames: 636/636 | 0 frames: 565/565 | 0 |
| Lenis `autoRaf: true`, no hookup | **1 frame: 636/636** | **1 frame: 565/565** | 76 / 74 scroll px (p95 26 / 36) |
| Lenis `autoRaf: true` + `lenis.on('scroll', ScrollTrigger.update)` | 0: 636/636 | 0: 564/564 | 0 |
| native, no Lenis | 0: 54/54 | 0: 54/54 | 0 |

Without the hookup, ScrollTrigger updates on the browser's `scroll` event, which arrives in the frame after Lenis's `scrollTo`. The `scroll` hookup alone removes the lag. Driving Lenis from the ticker is what puts everything else on GSAP's clock after Lenis: numeric scrub, `quickTo`, other ticker listeners, R3F `advance()`.

**(b) Motion.** Lag of the `useScroll()` value written by hand:

| Lenis driver | Chromium | WebKit | `useSpring` best-fit delay (Cr / WK) |
|---|---|---|---|
| `frame.update(({ timestamp }) => lenis.raf(timestamp), true)` | **1 frame: 698/698** | **1 frame: 608/608** | 18 / 17 frames |
| Lenis `autoRaf: true` | 0: 630 · 1: 68 | 0: 541 · 1: 67 | 17 / 16–17 |
| `frame.setup(…)` + dispatch a `scroll` event on each Lenis scroll | 0: 699/699 | 0: 609/609 | 17 / 16 |
| native, no Lenis | 0: 63/63 | 0: 63/63 | 13–16 / 13–15 |

Motion measures `useScroll` only when a window `scroll` event fires. The browser dispatches that event in the frame after Lenis's `scrollTo`, and Motion reads it in its `read` step, which runs before `update`. So with `frame.update`, `useScroll` is always one frame late. With Lenis on its own rAF, the order of the rAF callbacks decides, which leaves about 10% of frames late (jitter). Driving Lenis in `frame.setup` and dispatching the event at once puts the read into the same batch. The spring (`stiffness 100, damping 30`) trails by 16–18 frames under every Lenis driver (median |spring − scrollTop| 209–251 px, max 547 px), so smoothing on top of Lenis costs about 0.3 s. Its input's one-frame lag is noise next to that.

**(c) R3F** (Chromium, WebGL via ANGLE on SwiftShader). Lenis runs on `gsap.ticker` unless noted:

| Canvas | Rendered in the frame | Lag |
|---|---|---|
| `frameloop="never"` + `advance(t)` from `gsap.ticker` after Lenis | 696/696 | 0: 696/696 |
| `frameloop="demand"` + `invalidate()` on Lenis `scroll` | 348/697 | 0: 348 · **1: 349** (every other frame; 148 renders per run against 370) |
| `frameloop="always"` (R3F's own rAF) | 698/698 | 0: 698, only because R3F's rAF happened to run after GSAP's; nothing guarantees that order |
| `demand` + `invalidate()`, Lenis `autoRaf: true` | 689/698 | **1: 698/698** (it renders before Lenis moves) |

When called outside `useFrame`, `invalidate()` sets the frame budget to 1. The loop renders once, stops, and the next `invalidate()` has to request a new rAF, which runs a frame later.

**Verdict.**
- **(a) Yes:** 0 frames with the ticker recipe, and exactly 1 frame without the `scroll` hookup.
- **(b) No for `frame.update`:** always 1 frame late. `frame.setup` plus a dispatched `scroll` event gets 0 frames.
- **(c) Yes for `advance()`:** 0 frames. `demand` + `invalidate()` is a frame late on every other frame.

**Rule.** Couple values in one tick, producer first: `gsap.ticker` → `lenis.raf` → `ScrollTrigger.update` → R3F `advance()` gives zero frames. Motion's `frame.update` leaves `useScroll` one frame behind Lenis, so drive Lenis in `frame.setup` and dispatch a `scroll` event, or let GSAP own the scene. `frameloop="demand"` + `invalidate()` is only for canvases that don't track the DOM.

**Caveats.** The `frame.setup` recipe depends on Motion's current internals (it measures on window `scroll`). The synthetic event also reaches other window `scroll` listeners; Lenis ignores it while smoothing. SwiftShader changes render cost, not the order of callbacks.

## S5 — ScrollTrigger progress on a CSS sticky range wrapper (Chromium, desktop)

**Question.** Can the GSAP adapter read ScrollTrigger progress instead of running its own `getBoundingClientRect` loop?

**Setup.** `pages/s5.html`: 600 px of content, then a 300vh wrapper whose child is `position: sticky; top: 0; height: 100lvh`, then 100vh. `ScrollTrigger.create({ trigger: wrapper, start: 'top top', end: 'bottom bottom' })`, no pin. Both native scroll and Lenis (the S4a ticker recipe).

**Method.** Compare `st.progress` with v1's `clamp01(-rect.top / (rect.height - innerHeight))` in the same end-of-frame sample. Conditions:
- 31 `scrollTo` positions plus a full wheel pass, at 1440×900, then 1280×720, then 390×844;
- 5 frames straight after each resize;
- 300 px added above the wrapper, before and after `ScrollTrigger.refresh()`;
- a read in the same callback as a programmatic `scrollTo`.

Max |ST − rect| (progress / px of the range; 0 means under 0.0005 px):

| Condition | Native | Lenis |
|---|---|---|
| 1440×900: 31 positions + 358 / 412 wheel frames | 0 / 0 px | 0 / 0 px |
| 1280×720 and 390×844, after ScrollTrigger's resize refresh | 0 / 0 px | 0 / 0 px |
| First frames after a resize, before that refresh | up to 0.10 / 144 px | up to 0.10 / 144 px |
| Resize event to refresh (separate probe, three resizes) | 183, 1 and 1 ms | not probed |
| 300 px added above the wrapper; ScrollTrigger did not refresh on its own | 0.167 / **300 px** | 0.167 / 300 px |
| …after `ScrollTrigger.refresh()` | 0 / 0 px | 0 / 0 px |
| Read in the same callback as `window.scrollTo(…)` | 0.458 / **825 px** (still the pre-jump value) | same |

**Verdict: yes.** Once refreshed, ScrollTrigger's progress is identical to the rect maths at every viewport, under native scroll and under Lenis. Every difference was staleness, never drift.

**Rule.** The GSAP adapter reads ScrollTrigger progress for a sticky range and owns its freshness: call `ScrollTrigger.refresh()` on any layout change above or inside the range (a ResizeObserver on `body`), and read in the tick after `ScrollTrigger.update`, never straight after a programmatic `scrollTo`.

**Caveats.** Measured on desktop Chromium only. On touch-only devices `ignoreMobileResize` is on by default, and it skips the refresh when only the height changes by less than 25%. So while the toolbars move, `end` keeps the old `innerHeight` and the rect formula does not. A `100lvh` pin also travels `rect.height − lvh`, so on phones with the toolbars shown both formulas run past the pin by the toolbar height. Settle that on the real-device pass.

### S6a — `autoSplit` and a late font

**Setup.** `pages/font.html`.
- The heading is 56 px with line-height 1. It takes 4 lines in the fallback font (Georgia) and 6 in the web font, Courier New.
- The preview server sends the web font 1 s after the request, with `font-display: swap`.
- An invisible, unsplit twin in the same box gives the correct line breaks.
- A script at the top of `<head>` records every `document.fonts` event.
- CLS comes from the Layout Instability API, which only Chromium has. Every engine also records, each frame, where the paragraph under the heading sits.

Every split uses `type: 'lines,words'`, `mask: 'lines'` and an `onSplit` that returns the reveal. The runner waits 2.8 s, then narrows the viewport to 700 px. `loadingdone` fired at 1,029–1,063 ms in Chromium and 1,043–1,112 ms in Firefox. **WebKit fired `loading` (9–47 ms) and never `loadingdone`.**

Each cell: the split's timing, whether the final lines equal the unsplit twin's (✓ or ✗; with the font in, the unsplit heading is 336 px), and how far the paragraph below moved when the font swapped.

| Mode | Chromium 153 | WebKit 26.6 | Firefox 155 |
|---|---|---|---|
| unsplit | +112 px · CLS 0.0263 | +112 px | +112 px |
| `autoSplit: true` | re-split 1 ms after `loadingdone`, before the next frame · ✓ · +112 px · CLS **0.0263** | **no re-split** · ✗, heading 448 px · +224 px | re-split 2 ms after `loadingdone`, but the frame before it showed the stale split · ✓ · +224 px, then −112 px |
| `autoSplit: false` | ✗, heading 448 px · +224 px · CLS **0.297** | ✗ 448 px · +224 px | ✗ 448 px · +224 px |
| `document.fonts.ready`, then split | split at 1,035 ms · ✓ · CLS 0.0263 · no re-split at 700 px (✗) | 1,017 ms · ✓ · ✗ at 700 px | 1,040 ms · ✓ · ✗ at 700 px |
| `.ready` or `document.fonts.load()`, then split with `autoSplit: true` | 1,032–1,035 ms · ✓ · CLS 0.0263 · re-split at 700 px ✓ | 1,028–1,066 ms · ✓ · re-split ✓ | 1,037–1,043 ms · ✓ · re-split ✓ |

Also measured:
- `document.fonts.ready` resolved after the font had loaded in all three engines, because layout had already requested it. `document.fonts.load()` waits for the font by definition.
- The reveal keeps its place across a re-split. The first line's `yPercent` reads 50, 49, 48, 47 through Chromium's re-split, and 51 → 50 in Firefox. So a tween returned from `onSplit` survives it, as report 5 says.
- `mask: 'lines'` wraps each line in `overflow: clip`, not the `visibility: clip` report 5 describes.
- WebKit's `FontFace.status` reads `"error"` while the face is loading.
- An earlier version of the page had only the heading and one sentence. WebKit didn't paint it until the font arrived (FCP 1,039–1,080 ms). With a paragraph of fallback-font text it painted at 10–102 ms, which is why the fixture has one.

**Verdict.**
- **Chromium: yes.** autoSplit re-splits on `loadingdone` before the first frame in the new font, so it adds no CLS: 0.0263, the same as the unsplit page's font swap.
- **Firefox: yes, one frame late.** The event arrives after one frame has shown the stale split in the new font.
- **WebKit 26.6: no.** It never fires `loadingdone`, which is the only font signal autoSplit listens for. The fallback's 4 lines each re-wrap in the new font and stay that way until a resize.
- A split made in the wrong font costs 11× the swap's own CLS (0.297 against 0.0263). When the split waits for the font, the final lines equal the unsplit text in all three engines.

**Rule.** Split once the font is in: `document.fonts.load('<weight> <size> <family>')`, then `SplitText.create` with `autoSplit: true` (for width changes) and `onSplit` returning the reveal. Safari 26 never fires the `loadingdone` event autoSplit waits for, so a split made earlier keeps the fallback font's line breaks, and a wrong split costs 11× the font swap's own CLS.

**Caveats.**
- WebKit is Playwright's build, not Safari. Confirm the missing `loadingdone` on the real-device pass. The result was the same with the font delayed by Playwright's request interception (an earlier run) and by the server.
- Splitting after the font means the heading shows unsplit in the fallback until then, about 1 s here.

### S6b — The `aria` modes

**Setup.** `pages/aria.html`: an `h1`, and a `p` containing a link and an `<em>`, both split `type: 'lines,words'`. Three readouts:
- `locator.ariaSnapshot()`. Playwright computes this tree with its own algorithm, the same in every engine.
- Chromium's own tree, through CDP `Accessibility.getFullAXTree`.
- One press of Tab.

| `aria` | Heading (ariaSnapshot) | Paragraph (ariaSnapshot) | Chromium's own tree | Tab |
|---|---|---|---|---|
| unsplit | `heading "Every line arrives when its reader does"` | text, `link "screen readers"`, emphasis | the same | lands on the link |
| `'auto'` (the default) | the same name, from `aria-label` | `- paragraph`: no name, no content | paragraph named by the `aria-label`, no text, **no link node** | lands on the link, which is inside an `aria-hidden` line |
| `'hidden'` | absent | absent | neither exists | lands on the link, inside `aria-hidden` |
| `'none'` | the same name | the same as unsplit | the same, the text in word fragments | lands on the link |

**Why.**
- `'auto'` sets `aria-label` on the split element and `aria-hidden="true"` on every line, word and character wrapper. On a heading, that is a valid name.
- Role paragraph prohibits naming, so a spec-following tree (Playwright's) drops the label and is left with no content.
- A link inside a split paragraph is moved into a line wrapper, which is `aria-hidden`. It leaves the tree but not the Tab order.
- `'hidden'` puts `aria-hidden` on the element itself.

**Verdict.**
- **`'auto'` is right for headings only.**
- **`'hidden'` removes the element**, so the author has to supply the text some other way.
- ariaSnapshot is identical in all three engines, since Playwright computes it. Chromium's own tree agrees, except that it still exposes the paragraph's prohibited label.

**Rule.** Use SplitText's default `aria: 'auto'` on headings only. On a paragraph it hides the text behind an `aria-label` that role paragraph prohibits, and it drops any link inside a split line from the accessibility tree while the link stays focusable. Running text gets a visually hidden full copy plus `aria-hidden` pieces, or isn't split.

**Caveats.**
- WebKit's Tab skips links by default (it focused nothing in every mode, unsplit included), so the focus check covers Chromium and Firefox only.
- What a screen reader speaks for `'none'`, where the text arrives in word fragments, isn't measured.

### S6c — React re-rendering split text

**Setup.** `src/react.jsx`. Seven variants, each in its own React root, render `<h1>{text}{suffix && <em> (beta)</em>}</h1>` and split it `type: 'lines,words'`, `mask: 'lines'`. Every parent goes through five steps: mount, the same props, new text, the suffix removed, the first text again. Each step is a `flushSync` followed by 3 frames.

| Variant | Same props | New text | Suffix removed |
|---|---|---|---|
| split in `useEffect` on mount, no cleanup | ok | **old text on screen**, no error | **`NotFoundError` from `removeChild`; root unmounted** |
| `useGSAP(split, { dependencies })` | ok | old text | `NotFoundError`, unmounted |
| `useGSAP(split, { dependencies, revertOnUpdate: true })` | ok | old text | `NotFoundError`, unmounted |
| `dangerouslySetInnerHTML` + `revertOnUpdate` | ok | old text | old text |
| **keyed**: `<h1 key={text + suffix}>`, `useGSAP` with no dependencies | ok | ok | ok |
| **unowned**: React renders an empty `<h1>`; the effect writes the text, then splits | ok | ok | ok |
| **React-rendered words**: one `<span>` per word, GSAP animates them, no SplitText | ok | ok | ok |

It's the same in all three engines; only the error message differs:
- Chromium: "Failed to execute 'removeChild' on 'Node'".
- WebKit: "The object can not be found here."
- Firefox: "Node.removeChild: The node to be removed is not a child of this node".

**Why.**
- SplitText removes the text node React holds. `revert()` then restores the element with `innerHTML = snapshot`, which creates new nodes, so React's text node stays detached.
- On new text, React commits the change into its detached node. The cleanup's revert restores the old snapshot, and the effect splits it again.
- The `<em>` had been moved into a line wrapper, so React's `h1.removeChild(em)` throws.
- With `dangerouslySetInnerHTML`, React writes the new HTML, and the cleanup's revert overwrites it with the old snapshot.

**Verdict.**
- **React doesn't restore the text.** New text silently leaves the old split on screen. Removing an element React placed throws and unmounts the whole root.
- **Reverting in `useGSAP` doesn't help**, with either setting.
- **Three patterns work:** a key that remounts the split element when its content changes, React rendering the pieces itself, or text React never owns.

**Rule.** Never let React update text that SplitText has split. Key the split element by its content (`<h1 key={text}>`, split in `useGSAP`, reverted on unmount), or let React render the pieces itself. `revert()` restores a stale `innerHTML` snapshot and leaves React's text node detached, so reverting on update shows the old text, and React's next structural change throws.

**Caveats.** Production React only; StrictMode's development double-invoke wasn't run.

### S6e — `Intl.Segmenter`

**Setup.** `pages/segmenter.html`: a Japanese, a Chinese and a Thai sentence (`src/samples.js`) in a 320 px column at 20 px. Each sentence appears four times:
- unsplit: the engine's own line breaks, read one grapheme at a time;
- SplitText `type: 'words,lines'` as it comes;
- SplitText with `prepareText` inserting U+200B at `Intl.Segmenter` word boundaries, plus `wordDelimiter: { delimiter: /\u200B/, replaceWith: '' }`;
- the same, with punctuation (`\p{P}`) glued to the word before it.

Node 24.16 (ICU 78.3) segments the same sentences as a reference.

| | ja | zh | th |
|---|---|---|---|
| Segments: Chromium = WebKit = Node | 22 | 17 | 19 |
| Firefox 155 | 22, but different: は·まだ becomes はま·だ. で, ある, 無い and ぬ aren't word-like | 17: 出发 and 头 aren't word-like | 17: ติด·กัน becomes ติดกัน, เว้น·วรรค becomes เว้นวรรค, and คำ isn't word-like |
| SplitText as it comes: words / lines (lines rendered) | 1 / 1 (3) | 1 / 1 (2) | 2 / 2 (3) |
| With the segmenter: lines equal unsplit | ✗ in all three: a line starts with 。 | ✓ (WebKit ✗) | ✓ |
| With the segmenter, punctuation glued | ✓ in all three | ✓ (WebKit ✗) | ✓ |

**Verdict.**
- **Supported in all three engines.**
- Chromium and WebKit segment exactly like Node.
- **Firefox 155 segments all three samples differently** and marks some real words `isWordLike: false`, so `isWordLike` can't serve as a punctuation test.
- SplitText splits words only at spaces. A Japanese or Chinese sentence becomes one "word" and one "line" while it renders on 2–3 lines.
- Segmenter words give real lines once punctuation is kept with its word.

**Rule.** Segment CJK and Thai on the server with `Intl.Segmenter` (Node matches Chromium and WebKit; Firefox differs), keep punctuation (`\p{P}`) on the word before it, and hand the boundaries to SplitText through `prepareText` plus `wordDelimiter: { delimiter: /\u200B/, replaceWith: '' }`. SplitText itself splits words only at spaces.

**Caveats.** One sentence per language. Segmentation quality over longer text isn't measured.

| `view()` + `scroll(root)` on one element | both exact | both exact | both exact |
| `animation: reveal 1s …` | the same as `auto` | the same | the same |
| `animation-timeline` before the shorthand | the shorthand resets it: a 0 s `DocumentTimeline` animation held at its end state | the same | the same |

"0" means under 0.00005.

Firefox 155 as shipped showed every guarded box's static style (opacity 1, 40 px, no animation) at every offset. The unguarded recipes ran on the document timeline:
- `animation: fadeUp linear both` (report 1): a 0 s animation that finishes at once and holds its last keyframe.
- `animation: fade-up linear` (report 6): nothing attached.
- `animation: fadeUp 1s linear both`: a 1 s fade at page load (opacity 0.16 at 246 ms, 0.57 at 655 ms) on a box 1,500 px below the fold.

**Verdict.**
- **Chromium and WebKit: yes.** Both follow the spec's range maths exactly.
- **Firefox 155: `@supports` is false**, and the guarded static fallback applies.
- Report 6 §2.7 is wrong on three counts:
  - "only compositable properties animate": `margin-left` is exact;
  - "one timeline reference per element": two timelines on one element are both exact;
  - "no `@supports` needed since unsupported browsers simply never run the keyframes": Firefox runs them on the document timeline. That's harmless at 0 s and a visible fade on load with a duration.
- Its "ranges use the untransformed box" holds.

**Rule.** Put `view()` effects inside `@supports (animation-timeline: view())`, make the static style the finished state, and declare `animation-timeline` after the `animation` shorthand, which resets it. Chromium and Safari 26 then follow the spec's range maths exactly. Firefox 155 shows the static state, and an unguarded recipe with a duration plays once at page load there.

**Caveats.**
- Boundary quirks that change no value:
  - At exactly the timeline's end (cover 100%), WebKit's `getComputedTiming()` returns progress 1 for a fill-none animation whose range ended earlier.
  - At exactly a fill-none range's end, Firefox returns 1 where Chromium and WebKit return null.
- Readouts at rest only; S1 measured the moving case.

### S7b — `timeline-scope`

**Setup.** `pages/scope.html`. A subject in one column declares `view-timeline: --name`, and an element in the sibling column animates on `--name` over the default range (cover 0–100%). Five variants:
- `timeline-scope` on the common ancestor;
- no scope;
- the animated element inside the subject (the control);
- two unscoped stages sharing one name;
- the same pair with a scope on each stage.

| | Chromium | WebKit 26.6 | firefox-pref |
|---|---|---|---|
| Scoped | exact | exact (0.0003) | exact |
| Descendant (the control) | exact | exact | exact |
| No scope | **no timeline**: `timeline: null`, finished at progress 1, so it holds its last keyframe | **works** | **works** |
| Two unscoped stages, one name | neither has a timeline | **both follow the first stage's subject** | **both follow the last stage's subject** |
| Two stages, a scope each | each follows its own subject | the same | the same |

**Verdict: yes, `timeline-scope` works in Safari 26.**
- Safari and Firefox also resolve names without it, across the whole document: to the first (WebKit) or last (Firefox) timeline of that name.
- Chromium requires the scope.
- So a missing scope only shows up in Chrome. A repeated component without scopes binds to the wrong instance in Safari and Firefox.

**Rule.** Declare `timeline-scope` on the nearest common ancestor, one per component instance, whenever a named timeline drives an element outside its own subtree. Chromium requires it, and Safari 26 and Firefox silently bind an unscoped name to another instance's timeline, so a missing scope passes in Safari and fails in Chrome.

### S7c — Ancestors that clip

**Setup.** `pages/clip*.html`:
- a 200 px subject inside a wrapper with 50 px padding, once for each overflow value;
- a 300 px frame holding a 500 px child (the image-parallax shape), with `overflow: hidden` or `clip`, and once with the frame naming its own `view-timeline` for the child;
- two page-level pages, with `overflow-x: hidden` on `body`, and on both `html` and `body`.

| Ancestor | Timeline source | Progress while the page scrolls past (all three engines) |
|---|---|---|
| none, `overflow: clip` or `overflow-x: clip` | `html` | tracks the page (error 0; WebKit ≤ 0.0004) |
| `overflow: hidden` or `overflow-x: hidden`, on a wrapper that grows with its content | the wrapper | **frozen at 0.5** |
| a frame with `overflow: hidden` | the frame | **frozen at 0.375** |
| the same frame naming `view-timeline: --frame`, the child on `--frame` | `html` | tracks the page |
| a frame with `overflow: clip` | `html` | tracks the page |
| `body { overflow-x: hidden }` | `html` (the value moves to the viewport) | tracks the page |
| `html, body { overflow-x: hidden }` | **`body`** | **frozen at 0.5** |

**Verdict.**
- `hidden` makes a scroll container, and `view()` binds to it. That includes `overflow-x: hidden`, whose other axis computes to `auto`.
- That container never scrolls, so progress freezes at the subject's fixed position inside it.
- `clip` doesn't make a scroll container, and the subject tracks the page. All three engines agree.

**Rule.** Keep `overflow: hidden` and `overflow-x: hidden` off every ancestor between a `view()` subject and the page scroller. Use `overflow: clip`, or name a `view-timeline` on the clipping box and animate by that name. Never set `overflow-x: hidden` on both `html` and `body`, because it makes `body` the scroller for every `view()` on the page.

### S7d — A sticky stack

**Setup.** `pages/sticky.html`: three 600 px cards, each `position: sticky; top: 0`, in one 1,800 px section starting at 1,200. Card 1 is stuck for scrollTop 1,200–2,400, card 2 for 1,800–2,400, and card 3 never (it sits in the last slot). The readouts:
- each card's own `view()` over cover, plus contain and exit on cards 1 and 2;
- a non-sticky child of card 1 with its own `view()`;
- a child of card N on card N+1's named timeline, over `entry`, with `timeline-scope` on the section.

Three models are scored at 145 positions:
- **A**: the layout box with no sticky offset;
- **B**: where the box is in that frame, sticky offset included;
- **C**: the range ends sit where the box, sticky offset included, actually crosses the viewport's edges, and progress is linear in scroll between them.

| Readout | Chromium and WebKit | firefox-pref |
|---|---|---|
| Card 1, its own cover | **C, exact: 600→3,000.** Model A would be 600→1,800 (error 0.5) | **B, exact**: held at 0.5 while stuck |
| Card 1, its own contain / exit | C: 1,200→2,400 / 2,400→3,000 | contain jumps at 1,200; exit 2,400→3,000 |
| Card 2, its own cover | C: 1,200→3,000 | B |
| Card 1's non-sticky child, its own cover | C: 700→2,900 (not 700→1,700) | B |
| Card N on card N+1's `entry` | **exact: 1,200→1,800 and 1,800→2,400** (all three models agree) | exact |
| Card 3, never stuck | exact | exact |

**Verdict.**
- Progress on a stuck card follows neither the static model nor one rule across engines.
- Chromium and WebKit stretch a stuck box's ranges over its stuck travel, and the ranges of everything inside it.
- Firefox freezes them.
- Neither gives what a stack wants, "shrink while the next card covers me". The next card's `entry` range gives exactly that in all three engines.

**Rule.** In a sticky stack, animate card N on card N+1's named view timeline (`animation-range: entry 0% entry 100%`, with `timeline-scope` on the stack), which runs exactly while the next card slides over. Never use a stuck card's own `view()`: Chromium and Safari stretch its ranges over the stuck travel, and Firefox freezes them.

**Caveats.** Firefox's behaviour is behind a pref and may change before it ships.

### S7e — The reduced-motion reset

**Setup.** `pages/reduced.html`, with `page.emulateMedia({ reducedMotion: 'reduce' })`. Seven boxes run on `view()` over cover, each with a different reduce treatment. Each reduce rule is one class more specific than the rule it overrides, so the cascade can't decide the result. The static style is the finished state. Readouts at five offsets across the range.

| Under `reduce` | Animations attached | Computed timeline / range | Values across the range |
|---|---|---|---|
| control, no reset | 1 | `view()` / cover | scrub (0.5 at mid-range) |
| `animation: none; animation-timeline: auto` | 0 | `auto` / `normal` | static |
| `animation: none` | 0 | **`auto` / `normal`**: the shorthand resets both | static |
| `animation-name: none` | 0 | `view()` / cover (inert) | static |
| `animation-timeline: none` | **1**: no timeline, finished at progress 1 | `none` | its last keyframe (`scale: 1`, not the static `none`) |
| `animation-duration: 0.01ms !important; animation-iteration-count: 1 !important` | 1 | `view()` | **still scrubs** (0.5 at mid-range) |
| the animation only inside `prefers-reduced-motion: no-preference` | 0 | `auto` | static |

Chromium, WebKit and firefox-pref agree exactly. Firefox as shipped attaches nothing in any case.

**Verdict.**
- **`animation: none; animation-timeline: auto` fully resets the element**, in all three engines.
- **`animation: none` alone leaves nothing attached.** The shorthand resets `animation-timeline` and `animation-range` itself, so the added `animation-timeline: auto` changes nothing.
- What does leave something attached is `animation-timeline: none`: the animation stays, holding its last keyframe.
- The common global duration reset doesn't stop scroll-driven animations at all.

**Rule.** Reset scroll-driven animations for reduced motion with `animation: none`, or gate them behind `prefers-reduced-motion: no-preference`. The shorthand already resets the timeline and range. A duration reset leaves them scrubbing, and `animation-timeline: none` leaves them attached, holding the last keyframe.

### S7f — A native `scroll(root)` progress bar (optional)

**Not re-run.** S1's native baseline is this measurement: fixed boxes on `scroll(root)` under native wheel scrolling, read from painted frames.
- `transform` painted in the frame in Chromium (36/36) and a frame late in 18 of 54 WebKit frames.
- `left` was a frame late in every frame in both engines (36/36 and 54/54).

**Rule.** Drive a progress bar with `transform`/`scale`, never `width` or `left`. On native scroll that is frame-exact in Chromium and at most one frame late in Safari 26, and a main-thread property is always a frame late.
